# エントリ001 実装状況（2026-11-10 時点）

対象：`docs/entry-001-sketch.md` の「BPL × CBR 融合」。この文書は実装の現状と、スケッチとの差分を正直に記録するためのもの。

## 実装済み

- 文字列変換の骨格：`dsl.py`（変換プログラムの表現と実行）、`cases.py`（事例ベース）、`solver.py`（テンプレート→再利用→修正→探索）、`demo.py`。
- 昇格 v1（`library.py`）：解けた事例のプログラムが同じ骨格で再帰したら、異なるリテラルをスロット化（反単一化、Plotkin 1970）して型テンプレートとしてライブラリに昇格させる。被覆された事例は「テンプレート＋バインディング」の参照として保存される。solve の順序は テンプレート→再利用→修正→探索 で、全経路のコストを `candidates_tested` で計測する。
- 修正（revise）ステップ＋修正履歴：再利用に失敗した候補（類似度ランキング上位3件）に単一編集を適用する。ティア順は 値置換→部品交換（swap）→部品挿入（insert）→部品削除（remove）で、いずれも1編集・決定的順序。solve 1回あたりの修正候補の試行は予算 `REVISE_CANDIDATE_LIMIT`=256 で頭打ち（ソース間で共有）。採用された編集は {kind, …} として事例の history に保存され、`cases.py` で往返する。編集記録の再生可能性（記録を適用すれば勝ちプログラムを再構成できること）はレビューで双方向に検証済み。
- レビュー体制：コーディング＝DeepSeek V4.1 Flash、コードレビュー＝Kimi K2.7 Code、意味論レビュー＝GLM-5.2（いずれも dsh の別プロファイル）。昇格 v1 は両レビューで計11件の指摘を受け全件修正。修正ステップはコードレビューで欠陥ゼロ、意味論レビューでは主張・文書面の指摘（後述の差分記録を含む）を受けて反映済み。

## 実測（自作デモ上。反復用の手応えであって、主張の証拠ではない）

- 8タスク全解決（構造ティア検証用の code-upper を追加）。テンプレート2件（support 4 と 3）。事例は 7/8 が参照として保存（code-upper はどのテンプレートにも被覆されない）。経路内訳は search=2 reuse=1 revise=3 template=2。
- 候補数：name-swap-semicolon は探索14件 → 修正経由4件、date-separator-dot は探索15件 → 修正経由13件。code-upper は探索でも値修正でも解けず（修正導入前は45件を空費して未解決）、部品交換（replace→upper）で22件で解決。
- 逆に、修正が失敗した date-separator は 6件 → 94件（再利用1＋修正88＋探索5）に悪化した。直せる修正が存在しないと判明するまで全ティアの列挙代を払うのがこの設計の固定費で、予算は最悪値を抑えるだけで、この固定費そのものは減らさない。
- サイズ収支は **+152 B** の赤字のまま（事例+ライブラリの合計が、全事例を具体プログラムで持つ場合より大きい）。+152 B が履歴導入後も不変なのは、履歴が比較の両辺に like-for-like で載るため相殺し、code-upper は両辺とも具体プログラムで差分0だから。履歴そのものは8事例合計で約1.1 KBの純増であり、「履歴は無料」ではない。これを圧縮対象にできるのは次段階の修正パターン昇格。

## スケッチとの差分（重要・未解消）

- **修正ステップはあるが、失敗箇所の診断はない。** 上位候補への編集列挙と全例一致判定による生成・検査であって、スケッチの「失敗箇所を局所修正する」が想定する失敗位置の同定は行わない。修正提案へのモデル併用も未使用（決定性優先のため明示的にスコープアウトした）。診断の欠如は、修正の固定費（上記94件）の根本原因でもある。
- **修正履歴は保存されるが、成功した1編集のみ。** history（path、source_case、edits[{kind,…}]）が全事例に付く。未記録なのは：失敗した修正試行、修正→探索への逸脱（フォールスルー）、複数編集、そして修正前プログラムの実際の出力（スケッチの事例スキーマの「実行結果」に相当するもの。再計算は可能だが保存はされていない）。したがって「適応の**成否**が型を育てる」仮説の「否」側は、まだ記録に残らない。
- 昇格が扱うのは依然として「解の骨格」で、「修正パターン」の昇格は未実装。ただし入力契約としての履歴は蓄積が始まっており、value/string 系の修正（区切りリテラルの差し替え）は早くも support 2 で族を跨いで再帰している。型はプログラム全体であって部品として合成はできず、solve の順序もスケッチの「事例優先」と逆の「型優先」のまま。
