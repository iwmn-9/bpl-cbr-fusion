# エントリ001 実装状況（2026-11-11 時点）

対象：`docs/entry-001-sketch.md` の「BPL × CBR 融合」。この文書は実装の現状と、スケッチとの差分を正直に記録するためのもの。

## 実装済み

- 文字列変換の骨格：`dsl.py`（変換プログラムの表現と実行）、`cases.py`（事例ベース）、`solver.py`（テンプレート→再利用→修正→探索）、`demo.py`。
- 昇格 v1（`library.py`）：解けた事例のプログラムが同じ骨格で再帰したら、異なるリテラルをスロット化（反単一化、Plotkin 1970）して型テンプレートとしてライブラリに昇格させる。被覆された事例は「テンプレート＋バインディング」の参照として保存される。solve の順序は テンプレート→再利用→修正→探索 で、全経路のコストを `candidates_tested` で計測する。
- 修正（revise）ステップ＋実行適格ゲート＋完全試行記録：再利用に失敗した候補（類似度ランキング上位3件）に単一編集を適用する。ティア順は 値置換→部品交換（swap）→部品挿入（insert）→部品削除（remove）で、いずれも1編集・決定的順序。値置換は常に試行し、構造ティアはソースプログラムが対象例の全入力で DslError なしに実行できるときのみ（実行適格ゲート。ブールで閾値なし。adaptation-guided retrieval（Smyth & Keane 1998）の「適応可能性が労力を導く」原則を、ランキングではなく修正ティアの選択に1ビット信号で適用した変種。検索ランキング自体は意図的に不変）。ゲート済み候補は生成されず予算も食わない。solve 1回あたりの修正候補の試行は予算 `REVISE_CANDIDATE_LIMIT`=256 で頭打ち（ソース間で共有）。solve は各段階の試行を `report["attempts"]` に全件記録する（テンプレート1件、再利用は事例ごとに最初の失敗例 {input, expected, actual}（DslError 時は actual=null）、修正はソースごとに value_tested／structural_tested／gated／behavior={passed, errors}、探索1件。未解決でも残る）。demo は reason を除いて history に保存し、`cases.py` で往返する。採用された編集は {kind, …} として事例の history に保存される（再生可能性はレビューで双方向に検証済み）。
- 代謝（admission・統計・保持）：解けた事例は格納前に `classify_admission` で absorbed（既存テンプレートの列挙で解ける）／redundant（既存事例の具体化プログラムで解ける）／novel（いずれでもない）のラベルを付ける。各事例は使用統計 stats（reuse_tested／reuse_wins／revise_attempts／revise_wins）を持ち、demo が solve ごとに attempts から加算する。`maintain()` は redundant 事例の削除を候補に、削除後に残り全事例＋削除対象の例題が再解決できる場合のみ確定する（CBR の utility problem、Smyth & Cunningham 1996）。削除された事例の統計はトゥームストーン（{task_id, admission, stats, decision}）として事例ベース側に残る（cases.json は {"removed", "cases"} の新形式で、旧形式のリストも読める）。削除時はテンプレートの support からも対象 ID を取り除く。
- 修正パターンの昇格 v1（`library.py`・`solver.py`・`demo.py`；`cases.py`・`dsl.py` は不変）：事例履歴の勝ち編集（history の edits）だけを編集種別ごとのキー（value→役割、swap→演算子名の対、insert/remove→演算子名）に抽象し、support（そのキーに抽象される勝ち編集を持つ distinct な task_id）が `MIN_SUPPORT_CASES` に達したものを `library.patterns` へ昇格する（`maybe_promote_patterns` を demo が `maybe_promote` の直後に呼ぶ。P番号はテンプレートと同じ単調カウンタで永続化・再利用なし。再マイニングは support の in-place 更新のみで溶解なし、support 空でも残る）。適用は value/string 系のみ（構造系 swap/insert/remove、および value/int・value/joiner は採掘のみ・適用なし）：revise のティア列挙の前に、ソースが string リテラルを持ち `_task_separators`（対象例の入力∪出力セパレータ）が空でないとき、リテラル×そのセパレータの値置換候補を support 降順→ID昇順で試行する（予算はティアと共有。勝てば編集記録に `pattern_id` が付き、試行記録には `pattern_tested` が載る）。候補生成は value ティアと同一 semantics・同一ドメインなので、パターン候補は常に value ティアの string 役割候補の部分集合になる（修正ラウンドで出力セパレータのみから入力∪出力へ拡張）。dedupe は canonical JSON で「パターン候補1件の試行につき、同プログラムのティア出現1件を吸収する」scoped 仕様：`candidates_tested` はテスト事象数であって distinct プログラム数ではなく（基線から テンプレート↔再利用・value↔swap の重複計上を含む。code-upper の22件は distinct 13プログラム）、この読みの下でパターンパスは計上を増やさず、パターン候補が勝つ場合は同じ string 候補位置なら計上は基線と等しく、value ティアが先に非 string 候補を試す構成では減り得る（呼び出し全体の厳密な global dedupe は基線自身の重複計上まで抑制して 22→21 と動いてしまうため、この scope を採用）。maintain の確定削除ではテンプレートと対称にパターン support からも削除 task_id を刈り取る（溶解なし）。
- レビュー体制：コーディング＝DeepSeek V4.1 Flash、コードレビュー＝Kimi K2.7 Code、意味論レビュー＝GLM-5.2（いずれも dsh の別プロファイル）。昇格 v1 は両レビューで計11件の指摘を受け全件修正。修正ステップはコードレビューで欠陥ゼロ、意味論レビューでは主張・文書面の指摘を受けて反映済み。代謝ラウンドはコードレビューで中核機構に欠陥なし（周縁4件）、意味論レビューで中程度3件（統計の削除耐性、サイズ台帳の同条件性、support の残存 ID）を受け、修正ラウンドで全件解消した。修正パターン昇格 v1 はコードレビューで全項目クリーン、意味論レビューでは dedupe の裁定（candidates_tested はテスト事象数であり、ブリーフの「1回だけ試せ」と「総数を動かすな」は両立不可能で、実装の scoped な吸収が両者を満たす最小解と確定）と中程度2件（パターンの実質は優先順位ヒントであること、候補集合と証拠のずれ）を受け、修正ラウンドで候補集合の入力∪出力への拡張・パターン support の剪定・引用の是正（適応ルール学習は Hanney & Keane 1996）を反映済み。

## スケッチとの差分（重要・未解消）

- **失敗箇所の診断は依然なし（固定費は一部のみ緩和）。** ゲートの判断材料は「ソースが対象で実行できるか」だけで、失敗位置の同定ではない。記録される失敗観測も最初の失敗例1件（reuse の first_failure）と全例の passed／errors 計数までで、例を跨いだ失敗の分布や出力間の距離は残らない。非実行ソースの構造列挙という固定費はゲートで消えたが、実行はするが修理不能なソースの列挙代は全額のまま。
- **検索ランキングは意図的に不変・決定はデータ待ち。** adaptation-guided retrieval に沿ったランキング変更は先送りした（ブリーフの決定）。今回記録した behavior={passed, errors} はゲートの入力には十分だがランキングの証拠には不十分：passed は「既に完全一致する例の数」で近さを測らず（今回の記録では passed は全行 0）、behavior は試行された修正ソースにしか付かず、現ランキングが弾いた候補にはデータが無い。決定には (i) 全再利用候補への behavior 記録、(ii) 距離付きの失敗観測（全例の actual）、(iii) 保存済み事例ベースを使ったオフラインでのランキング比較再生、が先決。
- **保持まわりの残件はラベルの意味論のみ。** admission ラベルは格納時点のイベント記録で、以後の昇格・削除では更新されない（novel と付いた事例が現在は参照、という読み違えを招く。kept 判定を受けた redundant 事例はラベルだけ見ると削除可能に見える）。トゥームストーン統計と（テンプレート・パターン両方の）support の掃除は修正ラウンドで解消済み。
- **修正パターン v1 の位置づけと既知の限界（次ラウンドの設計入力）。** value/string の修正パターンは実装されたが、キー（種別＋役割）は学習内容を捨てる（観測された from→to の値も、リテラルが入力側か出力側かも残らない）ため value/string は永遠に1枠で、複数の抽象を表現できない。support は「その編集クラスが勝った」ことを数え、「このパターンが効いた」ことではない。採掘は勝ち編集のみ・溶解なしのラチェットで、失敗適用は pattern_tested 計数として記録されるが未マイニング。適用は value/string のみ（swap/insert/remove と将来の value/int・value/joiner は採掘のみ）。パターン候補は value ティアの string 役割候補の部分集合なので探索範囲を広げず、revise 内の順序を変える優先順位ヒントである（合成時には参照されない）。テンプレートは依然プログラム全体で部品として合成できず、solve の順序もスケッチの「事例優先」と逆の「型優先」のまま。次ラウンドの入力は (a) 学習内容を伴うキー（観測された置換値、入力側／出力側の区別）、(b) 負証拠マイニング（pattern_tested 計数は記録済み、候補特定は決定的再実行で復元可能）、(c) 構造系パターンの適用条件（behavior／gated 記録）、(d) value/int・value/joiner の適用可否、(e) 溶解規則の検討。
